## 1. Frozen stage purpose

Foundation-006 closes the semantic authorization seam between durable command acceptance and transaction admission.

The Controller is the **durable enforcement/commit boundary**, not the generalized policy engine. An external or local policy evaluator is consumed through one narrow decision port. No command becomes `ADMITTED` merely because it was durably accepted, transport-authenticated, emitted by chat, or accompanied by mutable metadata.

The authoritative path is:

`OPEN transaction -> canonical authorization input -> policy decision candidate -> current-state re-read -> atomic durable admission commit -> ADMITTED or REJECTED`

A non-final/unsafe evaluation returns `DEFER` and leaves the transaction `OPEN`.

## 2. Engine-neutral policy port

Foundation-006 defines this semantic interface; implementation language syntax is illustrative:

```text
PolicyDecisionPort.evaluate(request) -> PolicyDecisionCandidate
```

`evaluate()` may perform reads/network I/O **outside** the Controller SQLite transaction. It may not mutate Controller state, provider state, scheduler state, worker state, qualification state or promotion state.

### AuthorizationRequestV1

Required fields:

- `schema = controller://schemas/authorization-request/v1`
- `transaction_id`
- `command_id`
- `command_fingerprint`
- `repository`
- `subject = {algorithm, oid}`
- `required_policy_version`
- `principal_refs[]` — opaque immutable evidence references/digests
- `delegation_refs[]` — opaque immutable evidence references/digests
- `transport_provenance[]` — bounded non-secret provenance facts
- `action = {command_type, action_class}`
- `context = {constraints, requested_completion_class, bounded_owner_facts[]}`

The Controller canonicalizes this structure and computes `input_digest = SHA256(canonical request)` before policy evaluation.

`action_class` and `requested_completion_class` are Controller vocabulary, not Book/Learning/Documents/Core semantic interpretation. Unknown classes fail closed.

## 3. PolicyDecisionCandidateV1

Required fields:

- `schema = controller://schemas/policy-decision-candidate/v1`
- `decision_id` — UUIDv7 or adapter-defined immutable ID accepted by profile
- `outcome` — exactly `ALLOW`, `DENY`, or `DEFER`
- `policy_version` — exact logical version string
- `policy_revision` — immutable non-empty revision/snapshot identity, never `latest`
- `policy_digest` — lowercase SHA-256 hex
- `input_digest` — lowercase SHA-256 hex and must equal Controller-computed input digest
- `reason_codes[]` — sorted unique bounded codes
- `determining_policy_ids[]` — sorted unique bounded identifiers
- `diagnostic_error_codes[]` — sorted unique bounded codes
- `principal_refs[]`
- `delegation_refs[]`
- `approval_refs[]`
- `approval_required` — boolean
- `completion_contract` — present only for ALLOW; frozen 002B contract schema
- `valid_until` — RFC3339 UTC timestamp or null

Unknown fields fail closed.

### Outcome normalization

The Controller normalizes a candidate to `DEFER` without terminal commit when any of these are true:

- required evidence is unavailable/stale/revoked according to its owner contract;
- `diagnostic_error_codes` is non-empty;
- `policy_version` does not exactly equal the command's `required_policy_version`;
- policy revision/digest is unavailable or malformed;
- `input_digest` does not match;
- `approval_required=true` and no valid approval reference is present;
- `valid_until` is already expired;
- current state changed after evaluation.

No missing/error path is promoted to ALLOW.

## 4. Durable AdmissionDecisionV1

Only terminal `ALLOW` or `DENY` candidates create an authoritative admission-decision row.

Canonical decision content:

- `schema = controller://schemas/admission-decision/v1`
- exact transaction/command/fingerprint/repository/subject bindings;
- normalized terminal outcome;
- exact policy version/revision/digest;
- exact authorization `input_digest`;
- bounded reason/policy/diagnostic codes;
- opaque principal/delegation/approval refs;
- `approval_required`;
- normalized completion contract for ALLOW, null for DENY;
- `valid_until`;
- `decision_fingerprint` computed by Controller over all semantic fields except itself;
- `committed_at` generated by Controller at commit.

The decision table is one-terminal-decision-per-transaction.

## 5. Schema migration lock

Controller schema version increments from 4 to 5.

Add table conceptually equivalent to:

```sql
CREATE TABLE admission_decisions(
  decision_id TEXT PRIMARY KEY,
  transaction_id TEXT NOT NULL UNIQUE REFERENCES transactions(transaction_id),
  command_id TEXT NOT NULL REFERENCES commands(command_id),
  command_fingerprint TEXT NOT NULL,
  repository TEXT NOT NULL,
  subject_algorithm TEXT NOT NULL,
  subject_oid TEXT NOT NULL,
  outcome TEXT NOT NULL CHECK(outcome IN ('ALLOW','DENY')),
  policy_version TEXT NOT NULL,
  policy_revision TEXT NOT NULL,
  policy_digest TEXT NOT NULL,
  input_digest TEXT NOT NULL,
  decision_fingerprint TEXT NOT NULL UNIQUE,
  reason_codes_json TEXT NOT NULL,
  determining_policy_ids_json TEXT NOT NULL,
  diagnostic_error_codes_json TEXT NOT NULL,
  principal_refs_json TEXT NOT NULL,
  delegation_refs_json TEXT NOT NULL,
  approval_refs_json TEXT NOT NULL,
  approval_required INTEGER NOT NULL CHECK(approval_required IN (0,1)),
  completion_contract_json TEXT,
  valid_until TEXT,
  committed_at TEXT NOT NULL
);
```

No raw policy source, secret, identity document or approval text belongs in this table.

`DEFER` is not inserted into `admission_decisions`; it is a reconciliation result. A bounded `admission.deferred` semantic event may be emitted only if the implementation can make repeated identical deferrals idempotent. Portable v1 may return DEFER without durable event rather than create noisy/non-idempotent evidence.

## 6. Decision fingerprint and idempotency

`decision_fingerprint = SHA256(canonical AdmissionDecisionV1 semantic body excluding decision_fingerprint and committed_at)`.

Commit rules:

1. no existing decision for transaction -> continue validation;
2. existing decision with same `decision_id` and same `decision_fingerprint` -> return existing result with `duplicate=true`;
3. existing decision with same transaction but different fingerprint -> `ADMISSION_DECISION_CONFLICT`;
4. reused `decision_id` for a different transaction -> `ADMISSION_DECISION_CONFLICT`;
5. never perform a second transaction state transition/event on exact replay.

## 7. Current-state commit algorithm

Policy evaluation and evidence resolution happen before entering `kernel.atomic()`.

Inside one atomic commit:

1. re-read transaction and require `OPEN` unless exact duplicate terminal decision already exists;
2. re-read command row and fingerprint;
3. verify transaction command ID/repository/subject match the authorization request and decision;
4. parse the immutable command payload and require exact `required_policy_version === decision.policy_version`;
5. verify decision `input_digest` equals Controller-computed request digest;
6. revalidate decision expiry against commit time;
7. invoke owner-supplied evidence-standing validators for referenced identity/delegation/approval receipts **before** entering the transaction or consume already-created validation receipts whose own contract guarantees standing through commit; no network I/O is allowed inside the DB transaction;
8. insert the terminal admission decision;
9. for ALLOW, write normalized completion contract and transition `OPEN -> ADMITTED` with decision ID/fingerprint in event data;
10. for DENY, transition `OPEN -> REJECTED` with bounded reason codes and decision ID/fingerprint;
11. commit once.

If a precondition is stale, no partial admission row/state transition remains.

## 8. Evidence-standing boundary

Foundation-006 does not parse identity/delegation/approval documents. It consumes opaque references plus a validator result/receipt from the owning authority.

A validator must answer only bounded standing questions needed for commit, for example:

- reference exists and identity/digest matches;
- bound command/subject/action matches where the owner contract requires it;
- not expired/revoked at validation time;
- validation profile/version.

Private source evidence remains with its owner.

No human approval, delegation, or identity is fabricated when validators are unavailable. Missing validation yields DEFER.

## 9. Completion contract lock

ALLOW must carry a completion contract accepted by frozen 002B normalization:

- operations: `none` or `all_succeeded`;
- qualification: `not_required` or `required`;
- promotion: `not_required` or `required`;
- promotion requires qualification.

The policy side may choose a stricter contract for the requested action. Foundation-006 does not weaken it. Once ALLOW commits, the contract is immutable through the admission interface.

DENY carries no completion contract.

## 10. Required policy version semantics

Version matching is **exact string equality** in v1. No SemVer ordering, `latest`, range interpretation or implicit fallback is authorized.

If a future policy authority needs ranges or compatibility sets, that requires an explicit versioned contract change.

## 11. Policy revision semantics

`policy_revision` identifies the exact active immutable snapshot used to evaluate the request. `policy_digest` supplies content identity under the selected adapter profile.

A mutable label is never sufficient evidence. A policy adapter that cannot identify the exact evaluated revision returns DEFER/error, never ALLOW.

## 12. Public authority surface

Add a narrow Foundation-006 admission port rather than giving ingress/scheduler/worker adapters raw mutation authority:

```text
createAdmissionPort(kernel, policyPort, evidenceValidators, profile)
  .reconcileTransaction(transactionId)
  .inspectDecision(transactionId)
```

Ingress adapters retain only command acceptance. Worker ports retain heartbeat/result methods. Scheduler/execution layers must consume ADMITTED state; they do not receive admission commit methods.

The raw `ControllerKernel` remains a trusted in-process substrate in v1. Foundation-006 does **not** claim to stop malicious code that already has direct database/kernel access; that is the same deployment/trusted-process boundary already documented for direct SQLite writers. Qualification instead proves no supported ingress/worker/scheduler adapter bypasses the admission port.

## 13. Reconciliation loop

`reconcileTransaction(transactionId)`:

1. read durable current state;
2. if terminal decision/state already exists, return stable terminal result;
3. if transaction is not OPEN, classify and stop;
4. build canonical authorization request from durable command/transaction plus owner-valid evidence references;
5. evaluate policy once through the port;
6. classify adapter failure; retry nowhere inside this method;
7. normalize unsafe/incomplete/error candidate to DEFER;
8. if DEFER, return bounded reason with no admission mutation;
9. obtain/validate external evidence standing outside DB transaction;
10. attempt atomic terminal commit against re-read current state;
11. on stale-state conflict, return `STALE_RECONCILE_INPUT`; outer reconciler may start a fresh pass.

No loop assumes read-after-write freshness from an external policy source.

## 14. Retry ownership

Foundation-006 performs no hidden policy retries.

An outer reconciliation driver may retry only classified transient policy/evidence read failures with finite exponential backoff + jitter and the same durable transaction identity. Authorization DENY, schema failure, decision conflict, policy-version mismatch, revoked evidence and invalid signatures/digests are not transient retries.

Stacked retry layers are forbidden.
