## 1. Design objective

Provide one authenticated local live command-intake boundary for the Node Controller without creating a second semantic command authority and without weakening the durable Git inbox.

The local transport must be safe under duplicate delivery, lost response, fake endpoint, stream fragmentation, malformed input, local endpoint crash residue and authenticated-but-semantically-unauthorized callers.

A successful local authentication means only: **the peer possessed a configured local transport credential for this connection**. It does not mean the command is admitted, execution-authorized, human-authorized, provider-authorized, qualified or promotable.

## 2. Selected transport

Use `node:net` IPC only:

- Windows: named pipe.
- POSIX: filesystem Unix-domain socket.

No TCP listener is permitted in Foundation-005.

`node:net` is a byte stream; it provides no command message boundary. Foundation-005 therefore owns explicit framing.

## 3. Endpoint identity

Input authority:

- canonical database path from Foundation-004 `resolveControllerRuntimePaths()`;
- current Controller `instance_id` from Foundation-004.

Derive:

`endpoint_token = sha256(utf8(canonical_database_path + "\0" + instance_id)).slice(0, 32 hex chars)`

Selected endpoints:

- Windows: `\\.\pipe\system-master-controller-v2-<endpoint_token>`
- POSIX: `<os.tmpdir()>/sm-controller-v2-<endpoint_token>.sock`

Rules:

1. Raw database path is not emitted into the endpoint name.
2. A new Controller instance receives a different endpoint identity.
3. Foundation-005 never deletes a pre-existing endpoint before bind based on PID, age, timestamp or status-file claims.
4. `EADDRINUSE` / named-pipe equivalent is fail-closed `LOCAL_ENDPOINT_IN_USE`.
5. On POSIX, after successful bind and before accepting commands, the service attempts to set its own socket path to mode `0600`; failure is `LOCAL_ENDPOINT_HARDENING_FAILED` and the server closes.
6. Normal close removes only the endpoint created by that service instance.
7. Endpoint path/name is a locator, not authentication authority.

## 4. Credential contract

A credential consists of:

- `key_id`: non-secret ASCII `[A-Za-z0-9._-]{1,64}`;
- `secret`: bytes, minimum 32 bytes, maximum 128 bytes;
- `principal_label`: non-secret configured provenance label matching `[A-Za-z0-9._:/-]{1,128}`.

Raw `secret` bytes are runtime-only. They may not be serialized into SQLite, Git, status JSON, endpoint names, protocol responses, logs, exception messages, qualification receipts or source fixtures.

This stage does not specify the production secret-distribution mechanism. Environment/service-account secret custody is a deployment evidence boundary.

## 5. Wire framing

Every wire message is:

- 4-byte unsigned big-endian payload length;
- exactly that many payload bytes.

The frame reader must handle arbitrary stream fragmentation and coalescing.

Hard bounds:

- authentication/challenge frame payload: <= 4 KiB;
- command request payload, including protocol header/MAC: <= 64 KiB;
- response payload: <= 64 KiB;
- a zero-length frame is invalid;
- a declared length above the stage limit is rejected before allocating/accumulating the declared body.

Exactly one command request is permitted per connection.

## 6. Mutual HMAC protocol

Protocol domain: `controller-local-ipc-hmac.v1`.
HMAC: SHA-256.
Server nonce: 32 cryptographically random bytes generated per accepted connection.
Digest comparisons: equal-length 32-byte buffers with `crypto.timingSafeEqual`.

### 6.1 Server challenge

The first payload is a strict canonical JSON object generated by the server:

```json
{
  "protocol":"controller-local-ipc-hmac.v1",
  "type":"challenge",
  "instance_id":"<controller-instance-id>",
  "key_id":"<key-id>",
  "nonce":"<base64url-32-bytes>",
  "server_mac":"<base64url-32-byte-hmac>"
}
```

`server_mac = HMAC(secret, domain("server") || NUL || instance_id || NUL || key_id || NUL || nonce_bytes)`.

The client validates protocol, expected instance identity, expected key ID, nonce length and `server_mac` **before sending command bytes**.

### 6.2 Authenticated request

The client sends a bounded binary payload:

- ASCII magic `SMC1` (4 bytes);
- message type `0x02` (1 byte);
- 32-byte `request_mac`;
- remaining bytes = exact UTF-8 request JSON bytes.

`request_digest = SHA256(request_json_bytes)`.

`request_mac = HMAC(secret, domain("request") || NUL || instance_id || NUL || key_id || NUL || nonce_bytes || NUL || request_digest)`.

The server verifies frame bounds, magic/type and HMAC before JSON parsing or durable mutation.

The challenge nonce is single-use. A second command/request on the connection is rejected and the connection is closed.

### 6.3 Authenticated response

The server response payload is:

- ASCII magic `SMC1`;
- message type `0x03`;
- 32-byte `response_mac`;
- exact UTF-8 canonical response JSON bytes.

`response_digest = SHA256(response_json_bytes)`.

`response_mac = HMAC(secret, domain("response") || NUL || instance_id || NUL || key_id || NUL || nonce_bytes || NUL || request_digest || NUL || response_digest)`.

The client verifies the response MAC before accepting the response as Controller output.

A fake endpoint that does not hold the credential can therefore neither authenticate itself to the client nor forge a Controller response.

## 7. Strict JSON requirement

Request parsing must reject duplicate object member names at **every nesting depth** before semantic projection. Plain `JSON.parse()` alone is not sufficient.

The build must provide a bounded strict JSON parser/validator with these properties:

- valid UTF-8 only;
- exactly one JSON value and it must be an object;
- RFC 8259 string escape handling;
- recursive duplicate-key rejection;
- finite nesting depth, default maximum 64;
- finite object/array member count consistent with frame bound;
- JSON numbers only; NaN/Infinity are impossible/invalid;
- no trailing non-whitespace bytes;
- parser returns ordinary null-prototype-safe data or otherwise prevents `__proto__`/constructor-key side effects during construction;
- parsing performs no dynamic code execution.

## 8. Local request schema

Allowed top-level fields only:

- `protocol_version` — exactly `1.0`;
- `command_id` — UUIDv7;
- `command_type` — non-empty string;
- `target` — frozen 002B target object `{repository, expected_subject}`;
- `preconditions` — JSON value accepted by frozen command semantics;
- `intent` — JSON value accepted by frozen command semantics;
- `constraints` — JSON value accepted by frozen command semantics;
- `required_policy_version` — non-empty string.

Forbidden client fields include, without limitation:

- `schema`;
- `created_at`;
- `issuer`;
- `fingerprint`;
- `controller_version` / `controller_commit_oid`;
- runtime `policy_version` / policy digest;
- worker identity;
- lease/fence identity;
- qualification state;
- promotion state;
- execution authority;
- `parent_transaction_id` / `relation_to_parent` until a current durable lineage contract exists.

Unknown fields fail closed.

## 9. Deterministic projection to frozen 002B command

After transport authentication and strict request validation, construct exactly one frozen command envelope:

- `protocol_version`: request `1.0`;
- `schema`: constant `controller://schemas/command/v1`;
- `command_id`: request value;
- `created_at`: deterministic RFC3339 UTC millisecond timestamp decoded from the UUIDv7 Unix-millisecond field;
- `issuer.principal`: configured credential `principal_label`;
- `issuer.source`: constant `local-ipc-hmac-v1`;
- `command_type`: request value;
- `target`: request value;
- `preconditions`: request value;
- `intent`: request value;
- `constraints`: request value;
- `required_policy_version`: request value.

Do not accept a client fingerprint. Compute the semantic fingerprint only through frozen 002B `commandFingerprint` / `acceptCommand`.

Invoke:

`kernel.acceptCommand(command, { controllerVersion: serverControllerVersion, policyVersion: serverPolicyVersion })`.

`serverControllerVersion` and actual transaction `serverPolicyVersion` are runtime configuration owned by the Controller, never request fields.

The same authenticated semantic request therefore maps to the same command bytes/fingerprint even after an unknown response and delayed retry. A server wall-clock timestamp is not part of projection.

The UUIDv7-derived `created_at` is identity metadata only; it is not evidence that a human or transport actually submitted the command at that real-world time.

## 10. Readiness and lifecycle composition

The local server may begin listening only after Foundation-004 process ownership is held and recovery has produced `runtime.ready === true`.

Every request re-checks readiness immediately before semantic mutation.

Shutdown ordering:

1. stop accepting new connections;
2. reject/close not-yet-mutated active sessions;
3. finish or boundedly terminate the one already-entered semantic mutation section;
4. close/unlink the local endpoint;
5. only then allow Foundation-004 to publish STOPPED/release ownership.

No intake request may mutate after ownership is released.

## 11. Transport authorization versus semantic authorization

The injected `issuer` is **transport provenance**, not a policy approval token. Later authorization code must not infer human identity, delegated authority or dangerous-operation approval solely from `issuer.source=local-ipc-hmac-v1` or a matching `principal_label`.

A successfully accepted local command remains an `OPEN` transaction. Foundation-005 must not call `admitTransaction`, `activateTransaction`, create worker leases, execute provider effects, run qualifications or perform promotion.

Dangerous commands therefore remain subject to later policy/approval/admission authority.

## 12. Idempotency / unknown-result rule

The frozen 002B kernel remains the only semantic duplicate authority:

- same command ID + same projected semantic command => return original transaction with `duplicate=true`;
- same command ID + different semantic command => stable `IDEMPOTENCY_CONFLICT`;
- disconnect after durable commit but before response => exact caller replay is safe and returns the original transaction;
- the local server never performs a second hidden semantic retry.

## 13. Durable-offline / wakeup fence

Foundation-005 is a live adapter. It does **not** claim that bytes sent while the Controller is offline are durable.

The Foundation-002D protected Git inbox remains the Controller's durable offline rediscovery path and the place where lost/duplicate wakeups are correctness-neutral.

A caller that requires offline persistence must use 002D or durably retain its own request and replay it. Local socket availability is never the only durable command authority.

## 14. Retry contract

Server: no automatic command retry.

Client helper: no automatic semantic retry in this stage. It returns a classified transport result so an outer reconciliation loop can decide whether to replay the exact request.

Retryable externally classified conditions may include connect timeout, connection reset before authenticated response, or temporary endpoint unavailability. Authentication failure, schema failure, parser failure, `IDEMPOTENCY_CONFLICT`, not-ready and protocol violations are not silently retried by the intake layer.

Any future retry wrapper must be single-owner, finite, exponential-backoff-with-jitter and idempotency-preserving; stacked retries are forbidden.

## 15. Stable response/rejection taxonomy

Success JSON:

- `protocol_version: "1.0"`
- `status: "ACCEPTED"`
- `command_id`
- `transaction_id`
- `duplicate: boolean`
- `fingerprint`

Bounded error JSON:

- `protocol_version: "1.0"`
- `status: "ERROR"`
- `error_code`

Initial stable error classes:

- `LOCAL_ENDPOINT_IN_USE`
- `LOCAL_ENDPOINT_HARDENING_FAILED`
- `TRANSPORT_FRAME_INVALID`
- `TRANSPORT_FRAME_TOO_LARGE`
- `TRANSPORT_AUTH_FAILED`
- `TRANSPORT_SERVER_AUTH_FAILED`
- `PROTOCOL_INVALID_UTF8`
- `PROTOCOL_INVALID_JSON`
- `PROTOCOL_DUPLICATE_KEY`
- `PROTOCOL_NESTING_LIMIT`
- `PROTOCOL_UNKNOWN_FIELD`
- `PROTOCOL_INVALID_REQUEST`
- `PROTOCOL_UNSUPPORTED_VERSION`
- `COMMAND_SCHEMA_INVALID`
- `CONTROLLER_NOT_READY`
- `IDEMPOTENCY_CONFLICT`
- `INTERNAL_ERROR`

Internal exception text, stack traces, raw command secrets and raw authentication material are never response fields.
