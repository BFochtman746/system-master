# CHAT-START-COMMAND-CONTRACT-001

Status: CANONICAL_CURRENT / TOPOLOGY-007 / PROGRAM-JOB-LOCKED
Repository: BFochtman746/system-master

## Purpose

Define short user commands that deterministically enter current System Master work without project restatement, archive rediscovery or chat-by-chat reconstruction.

## Canonical commands

- `Start today's System Master chat.` -> `MASTER_ROOT`
- `Start today's Core chat.` -> `CORE`
- `Start today's Learning chat.` -> `LEARNING`
- `Start today's Book chat.` -> `BOOK`
- `Start today's Documents chat.` -> `DOCUMENTS`
- `Start today's Spreadsheet/Data chat.` -> `SPREADSHEET_DATA`
- `Start today's Media chat.` -> `MEDIA`
- `Start today's Connected Actions chat.` -> `CONNECTED_ACTIONS`
- `Start today's Research/Knowledge chat.` -> `RESEARCH_KNOWLEDGE`
- `Start today's Programming chat.` -> `PROGRAMMING`
- `Let's start our Programming chat.` -> `PROGRAMMING`

A request to discuss Prose does not create a Prose chat role. PROSE is complete and terminally retired. Historical Prose questions read preserved evidence; any genuinely unfinished integration of preserved completed Prose capability opens BOOK as the owner. DOCUMENTS never receives Prose work.

A Programming command opens the admitted Programming peer at `SYSTEM_MASTER/PROGRAMMING` and loads its preserved continuity lock and system packet. Peer admission does not restart completed Programming foundation/build/assurance work.

Website Building is capability C40 inside PROGRAMMING. A website-building request therefore opens PROGRAMMING for construction/build/test/deployment-preparation semantics. Browser action policy and user/external side effects remain CONNECTED_ACTIONS or the applicable explicit external authority gate.

## Mandatory startup action

Upon a start command or a request to build/resume a known system:

1. fetch current repository state and read `governance/CURRENT-AUTHORITY.json`;
2. read the current morning pointer/manifest when available as a cache only;
3. read selected topology, program job lock and system completion status before completion/ownership claims;
4. read the selected system catalog before broad rediscovery;
5. if Programming is requested, read `programming_work_program_lock`, `programming_control_record` and `programming_system_packet` before rediscovery or implementation selection;
6. load the requested active owner packet/control record;
7. fetch the active owner's live canonical control ref/head; never fetch retired Prose control as a live owner control;
8. reconcile `AUTHORITY_DELTA` from durable evidence;
9. read current completion, obligation, expectation, repair and Second Shift state and reject selectors violating current owner/job/retirement locks;
10. compare topology execution-ready peers with Second Shift owner coverage; auto-provision missing coverage only for an already-declared execution-ready peer when machine-resolvable, never by creating a system and never for a retired system;
11. recover exact referenced historical research/spec/code/test/qualification evidence before proposing replacement work;
12. apply only material/current delta review to historically closed research unless a real reopen trigger is evidenced;
13. identify one current objective and executable next-step contract inside the requested active system's locked job;
14. only then respond.

Current peer owner roles are CORE, LEARNING, BOOK, DOCUMENTS, SPREADSHEET_DATA, MEDIA, CONNECTED_ACTIONS, RESEARCH_KNOWLEDGE and PROGRAMMING. MASTER_ROOT is product-root governance, not a peer. PROSE is not an active role.

## Required first response

Return `CHAT READY`, `CHAT READY WITH DECISION`, or `NOT READY`, plus where the system is, material delta, where it is going and one exact next step. Do not dump full history unless requested.

For Programming, report `ACTIVE_INCOMPLETE_PEER_SYSTEM__ADMITTED_FROM_PRESERVED_WORK_PROGRAM`, preserve prior Programming evidence continuity and continue the first genuinely unclosed Programming package. Do not reduce Programming to Knowledge Recovery and do not create Website Building as a separate peer.

## Zero-rediscovery rule

Do not ask the user to restate System Master, repository identity, active topology, prior work, archived research, Second Shift history, system job assignments, completion truth, Prose retirement or the existence of the Programming foundation program when current authority/catalog/source evidence can resolve those facts.

Do not restart sealed/completed work because a chat is new. Previously closed research is revisited only through its material current-delta/reopen rule.

If live state differs from a morning packet or generated system packet, use:

`EXPECTED -> LIVE LOOKUP -> AUTHORITY/JOB/COMPLETION RESOLUTION -> DELTA CLASSIFICATION -> RECONCILE -> CURRENT OBJECTIVE -> EXECUTE/NEXT STEP`

The current live owner/topology/job lock always outranks a generated packet.

## MASTER_ROOT role

MASTER_ROOT is the SYSTEM_MASTER product-root controller, not another peer system. Its locked job is to integrate all nine active peers without taking their product semantics.

## PROGRAMMING role

PROGRAMMING means `SYSTEM_MASTER/PROGRAMMING`, control ref `programming/control-v1`. It owns software-engineering semantics and preserves the existing Programming foundation/capability/build/test/assurance/source-code/Genesis evidence as continuity inputs.

Programming owns AUTOMATION, CODE and WEBSITE_BUILDING C40. Website Building includes site/web-app architecture, source construction, frontend/backend composition, build/test engineering, deployment preparation and maintenance/repair engineering. It does not grant credentials, domains/DNS changes, production hosting/publication or browser/user-side-effect authority.

## CORE / Knowledge Recovery support

CORE owns shared Foundation/Spine and integration infrastructure. While `SYSTEM-MASTER-KNOWLEDGE-RECOVERY-001` is selected, Programming proving-corpus source/custody/provenance recovery is the highest discretionary System Master support priority. This does not absorb Programming engineering into Core.

## Retired Prose rule

`governance/retirements/PROSE-SYSTEM-RETIREMENT-001.json` and historical Prose branches/receipts remain immutable provenance. Any metadata describing PROSE as active is stale and cannot dispatch. ADR-0005 remains the retirement authority; ADR-0006 does not alter that boundary.

## Continuation rule

A new chat is only a new working surface. Durable repository state, catalog/source indexes, continuity locks and completed evidence survive chat turnover. Completed work is never reopened merely because a conversation is fresh. Packet/phase/test completion never becomes whole-system completion unless current completion authority explicitly says so.
