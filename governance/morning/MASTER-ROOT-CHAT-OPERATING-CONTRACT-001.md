## GitHub write authorization invariant

A chat is a working surface, not repository authority. Once `SYSTEM-MASTER-GITHUB-RELIABILITY-CONTROL-PLANE-001` is admitted, MASTER_ROOT must use the shared GitHub work-lease and canonical-writer path for state-changing repository work.

- Routine implementation/research/test work proceeds autonomously on an isolated candidate branch inside the active work lease.
- MASTER_ROOT does not write `main` or another canonical owner control ref directly.
- Canonical admission requires the current owner-lane lease, global repository-writer fence, exact expected base SHA, qualified candidate, and controller admission.
- A stale owner head, stale base, expired/revoked lease, stale fence epoch, or divergent idempotency reuse fails closed for mutation while read-only inspection remains allowed.
- MASTER_ROOT cannot mint, widen or renew its own authorization merely because it has GitHub connector access.
- Replacing the central objective, changing topology/ownership boundaries, superseding another owner's material current work, cross-owner canonical writes, force mutation, failed-gate bypass, or permanent security/governance-policy changes require explicit user authority.
- Repository state is authoritative; chat memory is never sufficient mutation authority.

This invariant is specifically intended to let multiple chats work concurrently without allowing them to redefine or overwrite one another's canonical work.

## Second Shift invariant

MASTER_ROOT is the portfolio controller, not an active peer-worker lane. Active Second Shift lanes are discovered from `SECOND-SHIFT-REGISTRY-001.json::owner_files`; currently CORE, LEARNING, BOOK and DOCUMENTS.

There is no active SYSTEM_MASTER root worker lane and no active PROSE lane. Historical files for those former/temporary lanes remain evidence only.

Whenever product-root sequencing changes an active system's current objective, ensure that owner has a current registry-declared delegation or a valid all-rungs exhaustion proof. For Documents, objective movement is reconciled through `governance/second-shift/DOCUMENTS-DELEGATIONS.json`.

During Second Shift, completion, BLOCKED or STALE is not shift completion. The controller must re-read live authority, consume the terminal state idempotently, select/bind the next dependency-valid unattended-safe successor, and continue while the shift remains open. Watchdog schedules are recovery controls, not the authoritative semantic queue.

A new first-class system still requires explicit user instruction, a superseding topology ADR/registry and an owner lane. A tool is not demoted merely because its execution is headless through Chat.

## Retired Prose safeguard

If a current registry, packet, task or repair route points to PROSE, classify `RETIRED_OWNER_STALE_WORK`. Preserve historical evidence, then close/supersede or translate genuinely required work to DOCUMENTS. Never restore Prose as an active owner merely because historical branches or qualifications remain.

## Required current-state model

Before substantive execution, MASTER_ROOT must know current main, selected topology, current central objective, live controls/objectives for CORE/LEARNING/BOOK/DOCUMENTS, retired-Prose standing, current completion/open obligations, repair state, active Second Shift lanes/delegations, qualification boundaries, current GitHub write-control standing when admitted, and one exact next step.

## Anti-surprise

Repository movement is normal. Use `LIVE LOOKUP -> DELTA CLASSIFICATION -> RECONCILE -> CURRENT PRODUCT STATE -> NEXT STEP`. A new chat does not reset project state or completed evidence. A changed live Git head never authorizes last-writer-wins behavior; stale mutation authority is discarded and reacquired through the controller.
