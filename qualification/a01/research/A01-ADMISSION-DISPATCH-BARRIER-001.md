# A01-ADMISSION-DISPATCH-BARRIER-001

Date: 2026-09-09
Owner: SYSTEM_MASTER shared A-01 control plane
Standing: RESEARCH_COMPLETE__IMPLEMENTATION_REQUIRED

## Problem

A qualification can be registered on canonical `main` after an existing workstream workflow run has already resolved `a01-control-plane-gateway.yml@main` to an older commit. Re-running only the failed job or an individual job then reuses the reusable workflow commit from the first attempt. The run therefore continues to see the old registry and can report `UNREGISTERED_QUALIFICATION` even though the qualification is present on current `main`.

Observed repository evidence:

- Run `34419309748` attempt 2 continued to reference reusable gateway SHA `581f5842f17fe191e9faa178c5b62d58008f08a2` and returned `UNREGISTERED_QUALIFICATION:BOOK-SYSTEM-LIFECYCLE-CURRENT-PARENT-COMPATIBILITY-ADAPTER-001`.
- A brand-new run `34419773379` resolved the same `@main` gateway reference to newer control-plane SHA `49dac6aa75a3b617092c0a20c66fa692ee04f5a2`, saw registry v26, and the unchanged exact subject `fc5adf8fd130d7b5324cff0058ab3804d75ec54e` passed A-01.
- The A-01 machine itself was healthy in both cases. The failure was control-plane freshness/admission, not runner availability or subject behavior.

## Current GitHub behavior verified from official documentation

1. Re-runs preserve the original event `GITHUB_SHA` and `GITHUB_REF`. GitHub also documents a special reusable-workflow rule: re-running failed jobs or a specific job uses the reusable workflow from the same commit SHA as the first attempt; re-running all jobs resolves a non-SHA reusable-workflow ref again.
   - https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs
   - https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations

2. For reusable workflows in the same repository, `uses: ./.github/workflows/<file>.yml` uses the called workflow from the same commit as the caller. This is the preferred mechanism when one immutable control-plane snapshot must govern the whole run.
   - https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows

3. `workflow_dispatch` can launch a fresh run against a named branch or tag. For `workflow_dispatch`, `GITHUB_SHA` is the last commit on the selected `GITHUB_REF` at dispatch time. The workflow file must exist on the default branch to receive the event.
   - https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows
   - https://docs.github.com/en/rest/actions/workflows

4. A repository `GITHUB_TOKEN` can trigger `workflow_dispatch` and `repository_dispatch` even though most other events generated by `GITHUB_TOKEN` do not recursively create workflow runs. The dispatch API requires Actions write permission.
   - https://docs.github.com/en/actions/concepts/security/github_token
   - https://docs.github.com/en/rest/actions/workflows

5. GitHub concurrency with `queue: max` supports up to 100 pending jobs/runs in a concurrency group. The existing `a01-global-r2` queue design is therefore valid and is not the cause of the stale-registry failures.
   - https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax
   - https://docs.github.com/en/actions/reference/limits

## Root causes

### RC-1 — mutable branch reference resolved too early

Workstream callers use `owner/repo/.github/workflows/a01-control-plane-gateway.yml@main`. GitHub resolves `main` when the run begins and records the resolved reusable-workflow commit.

### RC-2 — wrong retry primitive after control-plane change

A job-level/failed-job rerun intentionally reuses the original reusable-workflow SHA. If registry/policy/gateway authority changed after attempt 1, the rerun cannot see that change.

### RC-3 — registration discovery occurs too late

The current gateway discovers `UNREGISTERED_QUALIFICATION` only after the self-hosted A-01 job has been admitted and the Windows runner has been acquired. Registration freshness should be checked on a hosted runner before A-01 admission.

### RC-4 — two control-plane generations can be mixed

The current gateway qualification job checks out the canonical control plane at `job.workflow_sha`, but `repair_lineage_guard` checks out `ref: main`. If `main` advances between those operations, the same run can validate repair lineage from a newer generation while executing registry/policy from an older generation.

### RC-5 — receipts bind only the subject identity

Current A-01 receipts bind `subject_sha` and `checkout_sha`, policy version and registry version, but do not explicitly record the exact control-plane commit that interpreted those versions. The exact control-plane SHA should be part of request/evidence/receipt identity.

### RC-6 — branch-local qualification callers are being used as refresh mechanisms

Creating another workstream-specific caller works because it creates a new run, but it moves the workstream branch, creates extra workflows, and makes the refresh rule implicit instead of governed.

## Permanent architecture

The system must treat the qualification subject and the control plane as two independent immutable identities:

- `subject_sha` — bytes being qualified.
- `control_plane_sha` — exact registry/policy/gateway/broker bytes authorizing and interpreting the run.

### Admission path

`workstream hosted/prequalification`
→ `central admission request`
→ `fresh workflow_dispatch to canonical main`
→ `hosted admission barrier on dispatch-time main SHA`
→ `verify registration/workstream/wrapper/exact subject`
→ `same-commit local reusable gateway`
→ `global A-01 queue`
→ `exact subject execution`
→ `receipt containing subject SHA + control-plane SHA`

### Required invariants

1. A-01 MUST NOT be acquired until hosted admission verifies the qualification exists in the exact control-plane snapshot.
2. The broker MUST be dispatched fresh on canonical `main`; branch-local callers MUST NOT use a job-level rerun to refresh registry authority.
3. The broker MUST call the gateway using same-repository same-commit syntax (`./.github/workflows/a01-control-plane-gateway.yml`).
4. Central workflows already executing from canonical main, such as overnight scheduling, may call the gateway locally because caller and gateway are the same commit.
5. Repair reruns MUST use the same immutable control-plane snapshot for repair-lineage resolution and qualification execution.
6. Any registry/policy/gateway/broker change invalidates an old control-plane execution context. Retry requires a fresh broker dispatch.
7. A pure subject/infrastructure retry may preserve the same `subject_sha`, but its new authoritative receipt must state the newly selected `control_plane_sha`.
8. `UNREGISTERED_QUALIFICATION`, workstream mismatch, wrapper absence, subject checkout mismatch, or control-plane SHA mismatch are admission/control failures, not product/subject failures.
9. The shared gateway continues to reject arbitrary commands and executes only registry-owned Node wrappers.
10. The global `a01-global-r2` serialized queue remains authoritative for the physical A-01 runner.

## Retry matrix

| Condition | Same subject? | Re-run old job? | Fresh central dispatch? |
|---|---:|---:|---:|
| Subject failure; no control-plane change | maybe | permitted but not preferred | yes |
| A-01 transient infrastructure failure; no control-plane change | yes | permitted once by repair policy | yes |
| Qualification newly registered | yes | NO | REQUIRED |
| Registry/policy/gateway/broker changed | yes or no | NO | REQUIRED |
| Wrapper added to subject | no, subject changed | NO | REQUIRED after new hosted prequalification |
| Repair candidate changed bytes | no | NO | REQUIRED after exact-SHA prequalification |
| Overnight plan | plan-pinned | not for authority refresh | scheduler uses local same-commit gateway |

## Implementation decisions

ADOPT:

- Central `a01-admission-broker.yml` with `workflow_dispatch` as the normal cross-lane entry point.
- Hosted `a01-admission-preflight.js` barrier before self-hosted admission.
- Same-commit local reusable gateway call from the broker.
- Exact `control_plane_sha` binding in A-01 request and receipt evidence.
- Repair rerun migration from external `@main` gateway reference to same-commit local reference.
- Repair-lineage checkout pinned to the gateway control-plane SHA.
- Selftests covering stale registry, wrong control-plane SHA, wrong workstream, missing wrapper, exact subject checkout, and local-same-commit gateway topology.
- Explicit policy rule: control-plane changes require fresh dispatch; job-level rerun is not an authority refresh.

DO NOT ADOPT:

- Dynamically fetching latest registry inside an already-running old gateway. That would destroy reproducibility by mixing control-plane generations.
- Auto-registering arbitrary subject wrappers from workstream branches. Registration is a shared trust-root decision and must remain centrally governed.
- Replacing the global A-01 queue; it is functioning correctly.
- Moving qualification logic onto the user workstation outside the registered wrapper/control-plane contract.

## Migration rule

Existing historical workflow runs and exact-SHA receipts remain valid historical evidence. Existing workstream-specific gateway callers are legacy launch surfaces; they must not be used as an authority-refresh mechanism. New cross-lane A-01 admission must use the central admission broker. Central main workflows may use local same-commit gateway calls.

## PASS criteria for this repair

The repair is complete only when:

1. hosted selftests prove admission rejection before A-01 acquisition for stale/unregistered requests;
2. broker run binds dispatch-time `main` SHA and exact subject SHA independently;
3. broker calls gateway locally from the same commit;
4. gateway/receipt records and verifies the exact control-plane SHA;
5. repair rerun uses same-commit control-plane authority;
6. original control-plane, overnight, closed-loop repair, and enforcement regressions remain green;
7. canonical A-01 selftest passes on the exact repair branch SHA;
8. only then may the repair advance to canonical `main`.
